### 9. `STATE_AUDIO_PROCESSING` の調査メモ（コードを読んだ範囲）

対象：android.googlesource.com の AOSP `main`（packages/services/Telecomm の最新コミット `766788d`、2025-03-18。frameworks/base も同日取得）。**Pixel の実機の Telecom がこのコードと同じとは限らない。**

分かったこと：

- `android.telecom.Call#enterBackgroundAudioProcessing()` は `@SystemApi`（`@hide`）。Javadoc には「This method can only be called by the default dialer app.」とある（frameworks/base `telecomm/java/android/telecom/Call.java`）。SDK にないため、呼ぶなら HiddenApiBypass が要る
- **ところが Telecom 側では、呼び出し元が標準の電話アプリかを確認していない。**
  - `InCallAdapter.enterBackgroundAudioProcessing(String callId)` には `// TODO: enforce the extra permission.` とあるだけで、権限もパッケージも確認せずに `CallsManager.enterBackgroundAudioProcessing(call, mOwnerPackageName)` を呼ぶ（Telecomm `InCallAdapter.java` 418〜440行付近）
  - `CallsManager.enterBackgroundAudioProcessing` が確認するのは「Telecom が把握している通話か」「別の ACTIVE な通話がないか」「状態が RINGING か ACTIVE か」だけ。`requestingPackageName` は表示用のアプリ名（`setAudioProcessingRequestingApp`）に使われるだけ（`CallsManager.java` 3204〜3233行付近）
- `InCallAdapter` は、バインドされたすべての `InCallService` に渡される。`CONTROL_INCALL_EXPERIENCE` を持ち UI を出さないサービスは `IN_CALL_SERVICE_TYPE_NON_UI` として扱われ、同じように `setInCallAdapter(new InCallAdapter(..., パッケージ名))` を受け取る（`InCallController.java` 2540〜2580行、2636行付近）。つまり BCR や PoC と同じつなぎ方のアプリからも、コード上は呼べる
- `STATE_AUDIO_PROCESSING` への変化は、NON_UI のサービスにも通常の状態変化として届く（`ParcelableCallUtils.java` で `CallState.AUDIO_PROCESSING` → `Call.STATE_AUDIO_PROCESSING` に変換。サービスの種類による除外は見当たらない）
- この状態に入ると、Telecom は音声のフォーカスを外し（`NO_FOCUS`）、`AudioManager.setMode(MODE_CALL_SCREENING)` にする（`CallAudioModeStateMachine.java` 355〜359行付近）。`Call.java` の説明では「通話は端末上のアプリが音声を扱っている状態で、ユーザーには常駐通知以外は見えない」
- `AudioManager.getCallUplinkInjectionAudioTrack` は `MODE_CALL_SCREENING` でも使える（`getCallRedirectMode()` が `MODE_IN_CALL` / `MODE_CALL_SCREENING` / `MODE_CALL_REDIRECT` を PSTN 扱いにする）。条件は `isPstnCallAudioInterceptable()` が true であること（frameworks/base `AudioManager.java` 9339〜9348行、9405〜9420行付近）
- `CALL_AUDIO_INTERCEPTION` の保護レベルは `signature|privileged|role`。priv-app の許可リストに入れれば付与されうる（frameworks/base `core/res/AndroidManifest.xml`）

分からないこと（実機での確認が必要）：

- Pixel の Telecom に、AOSP にない呼び出し元の確認が足されていないか
- ACTIVE の通話を AUDIO_PROCESSING にしたとき、標準の電話アプリ（Google の電話アプリ）の画面がどうなるか、`exitBackgroundAudioProcessing(false)` で ACTIVE に戻せるか
- `MODE_CALL_SCREENING` で、端末のマイクが送話から外れるか（未解決 1 への別の解き方になりうる）

設計への影響：もし使えるなら、「マイクを止める」代わりに「通話を AUDIO_PROCESSING にして、送話は注入した音声だけにする」という方式が候補になる。ただし標準の電話アプリの表示や通話状態を変える操作なので、PoC の手順1〜6の結果を見てから、別の実験として扱う（今回の PoC には入れていない）。標準の電話アプリの置き換えはしない（ADR-010）。
